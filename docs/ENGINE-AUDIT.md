# Execution engine review — 2026-10-22

This review evaluates a proposed single-binary, payload-mutation and crash-register engine against the checked PHP CGI regression lab. It is a decision record for this repository, not a claim that a local process can be made completely isolated from its host.

| Proposal | Current evidence | Decision for this release |
| --- | --- | --- |
| Go or Rust executable with absolute-path spawning | The Python Windows runner already uses exact PHP executable paths, checks the official ZIP and every extracted file, and launches under a Windows Job. A guided launcher downloads pinned portable Python and PHP archives without a system-wide install. | Keep this path while its clean-start and recurrence checks are completed. A compiled release would need reproducible builds, dependency and source attestations, release integrity, and a signing/distribution plan. A language rewrite alone supplies none of those. |
| Mutate CGI payload streams to map corruption paths | The current claim concerns the included, hash-pinned upstream fixtures. Mutating them changes the experiment and expected result. | Exclude mutation from the release comparison. A future research mode would need a separate corpus, bounded input schema, independent expected outcomes, containment review and clear non-equivalence to the pinned regression result. |
| Replace Windows Job limits with “absolute” containment | Windows Job limits bound this process tree's committed memory, process count and lifetime; they do not deny network or filesystem access. The hosted test container requests `--network none`, a read-only root, non-root UID/GID, dropped capabilities, no-new-privileges, memory and PID limits, and dedicated writable mounts. The build host has network access. | Recommend the hosted workflow when isolation matters. Preserve the transparent Windows local path with its warning. Docker controls are checked from host metadata, but the kernel, daemon, build image and host runner remain trust boundaries. [AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) and Linux [seccomp](https://docs.kernel.org/userspace-api/seccomp_filter.html) would require their own deny/allow tests; neither name alone proves complete isolation. |
| 50 MB and 2 seconds | A guided patched run recorded 33.89 MiB peak aggregate Job committed memory, 40 cumulative Job processes and 4.415 seconds for the entire supervised event. Its JUnit suite time was 1.447848 seconds; these are different scopes and do not measure each child. A fresh later patched event recorded 33.91 MiB and 2.13 seconds; an older-reference event recorded 33.63 MiB and 2.11 seconds. The local bound is 256 MiB/16 active processes/90 seconds; the cloud container requests 512 MiB and a 120-second in-container timeout. | Do not impose the proposed caps without naming their units, accounting and scope. A 2-second whole-event deadline would have cut off these healthy observations; a per-child limit has not been evaluated. Tune from repeated measurements on intended hosts, preserving a resource-failure result distinct from a regression difference. [Windows Job](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information) and [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html) measure and enforce different quantities. |
| Intercept SIGSEGV and extract registers/address range from a wrapper | The current products record process exit, stdout/stderr, JUnit results and container metadata. A parent's signal notification does not supply a child's register snapshot. Debugger, ptrace, core-dump or sanitizer routes each change privilege, privacy, timing and sandbox assumptions. An exception instruction address does not establish the earlier corrupted memory range. | Keep raw crash-register and corruption-range claims out of release results. If needed, build a separate offline instrumented container that captures crash status and sanitizer logs under reviewed storage/retention rules, then validate it with a controlled synthetic crash. Do not weaken the regression container's dropped capabilities for telemetry. See [Linux signal information](https://man7.org/linux/man-pages/man2/sigaction.2.html), [Windows thread-context requirements](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadcontext), and [exception fields](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-exception_record). |

## Release evidence still needed

- Re-run the hosted workflow at the final source commit and check both jobs' artifacts, job summaries and bounded log evidence. The published comparison records an earlier commit.
- The guided Windows path has completed in separate current-host invocations: patched 8.5.12 selected cases passed, and the older 8.5.11 reference recorded the three selected failures. Replaying the first completed ID returned historical evidence with exit 2, an unchanged receipt and no observed PHP process; later fresh IDs ran. This does not establish behavior on a clean Windows machine without the Visual C++ runtime or test the interactive prompt/browser-opening path.
- Have a newcomer complete the documented fork, dispatch, result-read and local launch paths. Source review and automated checks do not establish that a nontechnical reader can finish them.

The security goal for this release is a truthful, reproducible, bounded defensive comparison with an understandable setup and result. Expanding into generated corruption inputs or register-level crash analysis would require separate measured claims and acceptance tests.
